# Changelog

## [Unreleased]
### Added
- **Agents tab — Browse button on Location**: `Browse…` button beside the Location field on the project strip opens a folder picker (`QFileDialog.getExistingDirectory`). Starts in the current location if it's an existing folder, else `~`. Picked path is persisted on the active Project record via the same focus-out path as manual edits.
- **Agents tab — working-directory hint on first run**: When the active project's Location is a real folder, the first goal sent to a team gets a directive prepended:
  ```
  [Working directory: <Location>]
  Use this absolute path as the working directory for every shell/file operation (pass it as cwd to shell tools). Create, read, and modify files only inside this folder unless I explicitly say otherwise.
  ```
  Sent **once per team instance** (not every Run) and re-sent only when Location changes mid-session. The orchestrator already has the cwd in its context after message 1; repeating it on every Run is noise and risks being mis-read as a new directive.
- **Agents tab — Trust writes checkbox**: New `trust_writes` flag on the Project model (default off, with forward-only `ALTER TABLE` migration). When checked AND Location resolves to a real folder, every Run materialises `<Location>/.claude/settings.local.json` with scoped `Read/Write/Edit(<Location>/**)` allow rules so the Claude CLI inside the team isn't blocked per file. Idempotent and merges with any pre-existing user rules.
- **Agents tab — User card with inline reply + external notify**: New `UserCard` banner (`desktop_app/widgets/user_card.py`) above the goal row. Idle gray border by default; blinks amber↔cyan when the team requests user input (currently driven by `ApprovalRequest`). Hosts a `Reply to the team — Enter to send` line + Send button that pipes through the main goal pipeline so existing run logic applies untouched. Reply field's enabled state mirrors `goal_input` — disabled while a run is in flight so a second submission can't kick off in parallel. A gear button opens a notify-settings dialog. Notify backend is pluggable (`core/notify/__init__.py`); Telegram is the first concrete impl — bot token + chat id, sent via stdlib `urllib` so no new dependency. Off by default; failures are logged and swallowed so the agent loop is never affected.
- **Code Artisan team (built-in)**: New 6-agent quality-first coding team at `LLM/core/agents/teams/code_artisan.json`. Strict chain `orchestrator → architect → coder → refactorer → critic → orchestrator → docs`. Architect produces a plan (no code), coder implements with tests, refactorer does surgical cleanup, critic gives 4-axis P0/P1/P2 verdict, docs only fires on user-facing changes. Orchestrator's prompt now carries an explicit **AMBIGUITY** guard — never invent a task from filesystem evidence (folder names, screenshots, zips), treat short replies (`go`/`go ahead`/`try now`) as continuations of an already-stated goal not new task statements, and when the user asks "did you do X?" where X was never stated, answer "you haven't asked me to do X yet" rather than invent X to save face.

### Fixed
- **Agents — original user goal evicted across long sessions**: The orchestrator's `_chat_history` accumulated across `team.run_goal()` calls. When the cumulative size passed `max_history_chars` (default 60K), `_build_messages`'s drop-oldest fallback popped from index 0 — i.e., the user's original goal — when compaction was disabled or its model_fn call failed. Result: the orchestrator silently lost the goal mid-session and started asking "what should I do?" or, worse, inferred a task from filesystem evidence. Fixed in `LLM/core/agents/agent.py` to drop from index 1 instead, so the original ask and the latest message both survive even when compaction can't run. Slightly over-budget with the goal intact beats within-budget but goal-less.
- **Agents — Trust writes was structurally a no-op**: `trust_writes` wrote `.claude/settings.local.json` into `<Project.location>/.claude/`, but the Claude CLI subprocess inherited the desktop app's launch dir (typically the OWLLM repo) as its working tree, so the trust file was never read. Fixed by adding an optional `cwd` kwarg to `dispatch_model_fn` in `core/agents/backends/base.py` that signature-checks each backend and forwards `cwd` only to opt-in backends. `ClaudeCLIBackend` and `CodexCLIBackend` (`backends/claude_cli.py`, `backends/codex_cli.py`) accept `cwd=` and pass it to `subprocess.run` — so the agent session is rooted at the project's Location, the trust rules apply, and CLI tools see the working tree the user actually wants edited. The agents page wraps `dispatch_model_fn` in a closure that captures `self._active_project.location` (when it's a real folder).
- **Code Artisan team relocated back to built-ins**: An earlier `78b5557` commit moved `code_artisan.json` from `LLM/core/agents/teams/` (tracked, ships to all users) into `LLM/data/team_templates/` (gitignored, per-user) treating it as a custom user template. It was meant to be a built-in. Put back at `LLM/core/agents/teams/code_artisan.json` so every install of OWLLM ships the team. Existing users with an already-instantiated team won't auto-upgrade their materialised agent definitions (template instantiation respects user edits) — re-instantiate to pick up the new prompt; the drop-oldest fix above is the structural fix that addresses the underlying failure mode regardless of prompt.

### Changed
- **Windows native launcher split (GUI + worker)**: `launcher.exe` is now a minimal `-mwindows` stub that starts `launcher_worker.exe` with `CREATE_NEW_CONSOLE` plus `SW_HIDE`; the worker then launches the real app with console Python (`python.exe`), not `pythonw.exe`, so the desktop process and unguarded console grandchildren inherit a hidden console instead of allocating visible throwaway consoles. Build both with `LLM/build_launcher.bat`. Debug: run `LAUNCHER_DEBUG.bat` manually if you need a visible console.

### Fixed
- **Boot-time window flash burst — actual root cause (Windows)**: After exhaustive process-tracking and HWND-event tracking proved the visible "dozens of CMD-like flashes" during startup were **not** subprocess windows, the source was identified as ~150 transient top-level Qt windows titled "OWLLM" being created and shown rapidly. Two distinct fixes were required:
  1. `LLM/smart_installer.py` was running ~67 `python.exe -c "import <pkg>; print(<pkg>.__version__)"` subprocesses during the requirements-checklist scan (one per package, with `subprocess_flags = {}` after the visibility-first reset). Replaced the 6 inline subprocess loops plus `_verify_import` and the same-Python branch of `_verify_torch` with two new helpers `_probe_module_version` / `_probe_module_importable` that use `importlib.metadata.version()` and `importlib.util.find_spec()` in-process when `check_python == sys.executable`. Foreign-venv probes (install-time only) still fall back to subprocess. Eliminated all ~67 boot-time subprocess flashes; verified by 1ms ToolHelp process tracker.
  2. `LLM/desktop_app/model_card_widget.py`: `ModelCard.__init__` and `DownloadedModelCard.__init__` instantiated every internal `QLabel(...)` and `QPushButton(...)` without passing `self` as the parent. Each parentless child briefly became a top-level "OWLLM"-titled HWND when `setVisible(True)` or stylesheet polish ran before the layout chain reached the QFrame. ~12 labels per card × ~12 cards = ~144 transient top-level windows during `_refresh_models`. Fixed by passing `self` as the parent to every `QLabel` / `QPushButton` constructor in the file. Also added explicit `parent=` kwargs at the `ModelCard(...)` / `DownloadedModelCard(...)` / `PackageCard(...)` call sites in `desktop_app/main.py` (`_refresh_models`, `_rebuild_model_card`, search results loop, `_refresh_requirements_grid`). Verified: 152 OWLLM-titled top-level windows reduced to 6 legitimate ones (splash, MainWindow, HybridFrameWindow + Qt internals), confirmed independently by both a `SetWinEventHook` HWND tracker (`LLM/tools/debug_window_tracker.py`) and a Python-level `QWidget.show` / `setVisible` tracer (`LLM/tools/trace_window_creation.py`, activated via `LOCALLLM_TRACE_WIDGETS=1`).
  3. `LLM/desktop_app/splash_screen.py` + the `__main__` startup block in `desktop_app/main.py`: removed the per-progress-tick `QApplication.processEvents()` calls that were flushing the entire pending event queue (HWND-creation, show, paint events for every widget the MainWindow was building) at progress-bar phase changes (50%, 90%, 100%). Replaced with synchronous `splash.repaint()` so only the splash itself repaints. The replacement is documented in a comment block at the call site explaining why `processEvents()` must never be reintroduced there.
- **Root-cause fix for CMD window flashes (Windows)**: Added a process-wide subprocess boundary guard at `LLM/core/win_subprocess_guard.py` that patches **every** Windows spawn path the app can reach: `subprocess.Popen.__init__`, `_winapi.CreateProcess`, `os.system`, `os.popen`, and `QProcess` (when the PySide6 API is available). All patches force `CREATE_NO_WINDOW` + hidden `STARTUPINFO`, respect explicit `CREATE_NEW_CONSOLE` opt-outs, are idempotent, and degrade to no-ops on non-Windows.
  Critically, the guard also **propagates to grandchild Python processes** via `LLM/sitecustomize.py`. Python auto-imports `sitecustomize` from any entry on `sys.path`/`PYTHONPATH` at interpreter startup, so every child Python we spawn (uvicorn, pip, health-check probes, onboarding workers) installs the guard at its own startup — meaning pip's internal compiler spawns and uvicorn's library subprocesses also run without consoles. The guard inserts `LLM/` into `PYTHONPATH` when installed so child processes inherit it transparently.
  Installed at: `desktop_app/main.py` (pre-import + re-applied post-PySide6-import), `scripts/llm_server_start.py`, `LAUNCHER.py`, `pip_worker.py`. Diagnostic: set `LOCALLLM_SPAWN_TRACE=1` to log every intercepted spawn to `~/localllm_spawn_trace.log` for pinpointing any remaining flash sources. Set `LOCALLLM_DISABLE_NOWINDOW_GUARD=1` to opt out in child processes.
  Note: PySide6 6.8.1 does NOT expose `QProcess.setCreateProcessArgumentsModifier`, so `apply_create_no_window` has historically been a silent no-op; the guard now logs this to the trace file when active. QProcess-spawned console children (training/inference/MCP sites) will only gain full console suppression on PySide6 versions that add the API.
- **Per-site subprocess flag fixes**: Added `CREATE_NO_WINDOW` + hidden `STARTUPINFO` to all runtime subprocess call sites in our own code so child console processes no longer pop visible consoles when spawned by the GUI. Key fixes in this pass:
  - `scripts/llm_server_start.py` now passes `_SUBPROCESS_FLAGS` to `python -m uvicorn` — eliminates the flash on every app restart that auto-resumes the last-used model (explains why a clean first launch did not flash but later restarts did).
  - `core/immutable_installer.py` now passes `self.subprocess_flags` to the venv `cmd /c rmdir` — eliminates the flash on the download/isolate page.
  - `tool_server/tools/git_tools.py` now threads a module-level `_GIT_FLAGS` into `git status` (mirroring the existing `_SHELL_FLAGS` pattern in `shell_tools.py`).
  - `tools/free_vram_now.py` now passes module-level `_SUBPROCESS_FLAGS` to all 3 calls (`taskkill`, `netstat`, `nvidia-smi`) invoked by the Free-VRAM button.
  - Prior pass in the same release also covered: `core/llm_server_manager.py` (2x netstat), `pip_worker.py` (pip Popen), `smart_installer.py` (rmdir + bulk pip install), `installer_v2.py` (venv rmdir), `desktop_app/mcp/github_importer.py` (pull + 2x clone), `core/runtime_manager.py` (vcredist installer), `core/training.py` (finetune Popen).
  - An AST-based scanner confirmed no runtime sites remain; the only untouched sites are Linux-only (`xdg-open`) or standalone dev/diagnostic scripts never invoked by the GUI (`diagnose_installation.py`, `embed_icon.py`, `update_icon.py`, `validate_compatibility_matrix.py`, `verify_installation.py`).
- **QProcess vs subprocess guard (Windows)**: The prior fixes patched Python's ``subprocess.Popen`` / ``_winapi.CreateProcess`` / ``QProcess`` **only where the QProcess API existed**. PySide6 6.8.1 has **no** ``setCreateProcessArgumentsModifier``; the fallback (swap ``python.exe`` → ``pythonw.exe``) does not help for every executable name and, critically, **Qt6Core spawns children with its own Win32 ``CreateProcess`` path**, which **never** goes through Python's hooks. Training and the Test-tab ``run_adapter.py`` flows therefore still flashed no matter how strong the process-wide guard was. Fixed by replacing those ``QProcess`` usages with ``desktop_app.process_utils.HiddenSubprocessRunner``, a small ``QObject`` that runs ``subprocess.Popen`` + ``CREATE_NO_WINDOW`` and mirrors the ``readyReadStandardOutput`` / ``finished`` signals. Also added ``core/python_exe_swap.py`` so ``python3.10.exe``-style venv names and ``py.exe`` / ``pyw.exe`` map consistently for any remaining ``QProcess`` call sites.
- **Per-model venv guard propagation (Windows)**: Root-cause fix for the "isolate button always flashes" and "restart flashes" regressions that remained after the main `.pth` + `PYTHONPATH` strategy landed. Each `LLM/.envs/<env_key>/.venv/` has its own isolated `site-packages`, so the main venv's `localllm_guard.pth` was never visible to per-model python.exe — every onboarding/isolate/probe spawned from a per-model venv started *without* the guard, and any grandchild it forked (pip build workers, setup.py compilers, git clones, etc.) produced visible console windows. Fixed by adding `install_guard_into_venv(venv_path)` and `sweep_install_guard_into_envs()` in `core/win_subprocess_guard.py`: both write a tiny `localllm_guard.pth` + `localllm_guard_boot.py` pair into the target venv's site-packages so its interpreter auto-imports the guard at startup. `install_windows_subprocess_guard()` now runs the sweep on main-app startup (covering all pre-existing per-model venvs), and both `core/envs/env_registry.py::_create_env()` and `core/environment_manager.py` install the guard immediately after each successful venv creation (before any pip install, so even first-install compiler spawns are hidden). Verified end-to-end: child python spawned from a per-model venv now logs intercepted spawns to the trace file with `cf=0x8000000` (CREATE_NO_WINDOW) applied.
